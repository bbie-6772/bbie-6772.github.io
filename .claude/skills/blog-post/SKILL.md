# blog-post

목표는 설명을 읽기 쉽게 다듬으면서도 저자가 왜 그렇게 접근했고 무엇을 확인하며 생각을 바꿨는지 남기는 것이다. 문체를 흉내 내기 위해 감정이나 시행착오를 만들어 넣지 않는다.

작성·수정 전에 [voice.md](voice.md)를 읽는다. 사용자에게 확인한 선호와 원문에서 관찰한 경향을 구별한다. 이번 대화의 구체적인 지시가 저장된 기준보다 우선한다.

## 요청에 맞춰 시작하기

- 새 글: 주제, 글의 목적, 자료와 실제 경험에서 빈 곳을 확인한다. 기존 시리즈면 인접 글의 번호·메타데이터·배너를 확인한다.
- 기존 글 수정: 원문에서 핵심 질문, 판단, 미해결 의문을 먼저 추려 보존한다. 이미 있는 답을 다시 묻지 않는다.
- 여러 글 검토: 사용자가 정한 범위와 순서를 따른다. 글별 발견 사항·실제 수정·남은 질문을 구별해 기록한다.

파일에 접근할 수 없으면 받은 본문으로 작업한다. 저장소 전체가 없다는 이유로 문체 작업을 막지 않는다. 저장소 접근이 필요한 시리즈 번호나 자산 경로는 확인 전 확정하지 않는다.

## 생각이 빠진 곳에서 대화하기

일반적인 선호는 매번 재확인하지 않는다. 글의 인과관계에 필요한 저자의 생각이나 경험이 빠졌을 때, 관련 질문만 짧게 묶어 묻는다. 사용 가능한 질문 도구 또는 일반 대화를 사용하며 특정 제품의 도구명에 의존하지 않는다.

필요에 따라 다음 중 고른다. 모든 글에 전부 질문하는 체크리스트가 아니다.

- 처음에는 어떻게 될 거라고 생각했나? 그렇게 예상한 근거는 무엇이었나?
- 다른 방법도 있었는데 이 접근을 택한 이유나 당시 제약은 무엇이었나?
- 설명을 다시 듣거나 직접 실행했을 때, 예상과 달랐던 관찰은 무엇이었나?
- 어느 설명·코드·로그 때문에 원인을 이해하게 됐나? 아직 추측인 부분도 있나?
- 지금 돌아보면 무엇이 아쉽고 무엇이 뿌듯한가? 다음에는 어떻게 판단할 것 같나?

특히 “바꾸니 됐다. 왜지?”라는 기록을 발견하면 원인을 저자에게 물어 확인한 뒤 이해에 도달하는 흐름으로 재구성한다. 조사로 알게 된 기술적 원인만으로 “나는 그때 이해했다”를 만들지 않는다.

답변이 없으면 해당 인과관계와 1인칭 깨달음은 확정하지 않는다. 확인된 기술 설명 등 독립적으로 가능한 부분은 진행하고, 필요한 질문을 별도로 남긴다. 사용자가 기억나지 않는다고 하면 당시 의문을 보존하고 현재 확인 가능한 설명을 구분한다.

금지되는 것은 미확인 내용을 저자의 실제 경험·감정·깨달음으로 서술하는 것뿐이다. 장치임이 드러나는 서술은 쓸 수 있다. 표기된 추정(`지금 와서 추측하면`, `당시엔 확인하지 못했지만`), 가정(`만약 ~라면`), 가상의 독자나 질문자, 의도적으로 과장한 도입이 여기 해당한다.

## 조사와 초안

기술적 주장과 버전·성능 수치는 공식 문서·코드·논문 등으로 검증한다. 출처가 다르면 적용 조건부터 구분한다. 사용자의 취향으로 사실관계를 결정하지 않는다. 검증할 수 없으면 한계를 명시한다.

짧은 메모로 내용을 구별한 뒤 작성한다.

- 저자가 제공하거나 확인한 경험·예상·감정·판단.
- 원문과 실행 결과에서 실제 확인한 사실.
- 이번에 조사한 기술 설명과 아직 확인할 질문.

이 구분은 작업용이다. 최종 글에 편집용 분류나 미확인 1인칭 경험을 노출하지 않는다. 예시 코드는 예시로 표시하고, 실행하지 않은 코드를 검증 완료라고 쓰지 않는다.

개인 경험이 중심인 글은 필요에 따라 `처음 생각 → 선택·시도 → 예상과 다른 관찰 → 확인한 이유 → 달라진 이해와 감정`으로 구성한다. 이 흐름을 모든 글의 고정 소제목으로 만들지 않는다. 개념 정리 글에는 존재하지 않는 실패 서사를 끼워 넣지 않는다.

두 흐름 말고도 고를 수 있다. 원본 로그에 주석을 다는 형식, 질문과 답, 실패한 시도만 모으기, 발견 하나만 짧게 남기기, 이미 쓴 글을 비판적으로 다시 보기. 익숙한 형식에서 벗어날 때는 목차로 먼저 합의한다.

문장·맞춤법·띄어쓰기는 읽기 좋게 교정하되, 저자의 주저함·확신 정도·혼잣말을 임의로 단정적인 설명으로 바꾸지 않는다. 이유가 달라지는 편집은 대화로 확인한다.

### 번역투와 빈 수식어

이번에 생성한 설명 문장에서 왼쪽이 보이면 오른쪽으로 바꾼다. 금지 목록이 아니라 교정 후보다.

| 나온 표현 | 바꿀 방향 |
|---|---|
| ~을 가지고 있다 | ~이 있다 |
| ~에 위치하다 | ~에 있다 |
| ~함에 있어 | ~할 때 |
| 되어지다 / 보여지다 / 쓰여지다 | 능동 또는 단일 피동 |
| ~중 하나다 | 무엇 중에서 왜 그것인지 |
| ~라고 할 수 있다 | 단정하거나 근거를 쓴다 |
| 중요한 역할을 한다 | 무엇이 어떻게 달라지는지 |
| 획기적 / 혁신적 / 무궁무진 | 무엇과 견줘 그런지 |
| ~에 대해 알아보겠습니다 | 본론 첫 문장으로 시작 |
| 이 도구는 시간을 단축시켜 줍니다 | 이 도구를 쓰면 시간이 줄어든다 |

이 교정은 이번에 생성한 설명 문장에만 적용한다. 저자가 직접 쓴 문장에는 맞춤법 수준만 손대며, 저자의 어투를 번역투로 오인해 고치지 않는다.

접속사는 단어 자체가 아니라 문단마다 반복되는 것이 문제다. `또한`, `따라서`가 문단 첫머리에 세 번 이상 오면 연결어 없이 이어지는지 본다. 단어를 금지어로 만들지 않는다.

`scripts/post-lint.py`는 이 중 기계로 판정 가능한 것만 `문체 후보:` WARN으로 알린다. WARN은 판정이 아니라 확인 요청이다.

## 구조와 독자

독자가 필요한 배경을 따라올 수 있도록 용어를 풀어 설명한다. 독자 수준은 주제와 요청에 맞추고, 모든 글을 특정 연령에 맞추거나 쉬운 비유로 늘리지 않는다.

- 긴 학습 글에는 개요, 개념별 본문, 정리가 유용하다. 짧은 회고는 짧게 완결한다.
- 표는 실제 비교할 항목이 있을 때, 인용은 강조할 핵심이 있을 때 사용한다.
- 비유는 이해를 돕는 경우에 쓴다. 독자가 비유를 사실로 오해할 수 있을 때만 한계를 덧붙이고, 한 줄 비유에 매번 단서를 달지 않는다. 알고 있는 기술과의 비교는 자연스러운 연결이 확인될 때 사용한다.
- 이미지·인용·소제목·문단·줄 수의 할당량을 두지 않는다. `### 더 쉬운 비유로`를 자동 삽입하지 않는다.
- `한줄 평`은 익숙한 선택지다. 원문·시리즈의 관례를 존중하되 제목과 정확한 줄 수를 강제하지 않는다. 감정과 다음 행동을 매번 만들어 붙이지 않는다.

## 파일과 시각자료

Jekyll 파일을 작성하거나 검증할 때만 [jekyll.md](jekyll.md)를 읽는다. 기존 배너·자산·링크를 보존하고 새 파일명·게시일·시리즈 번호는 요청과 저장소를 기준으로 정한다.

실제 화면·로그가 주장에 필요하면 어떤 장면이 필요한지 구체적으로 요청한다. 그림이 없어도 설명이 충분하면 이미지를 요구하지 않는다. 자료가 없을 때 생성 이미지로 실제 실험이나 화면을 가장하지 않는다. 개념도는 설명용임이 드러나도록 만든다.

목차나 짧은 문체 예시로 합의를 확인할 필요가 있으면 먼저 보여준다. 이미 명확하게 승인된 방향의 편집에 단계별 재승인을 요구하지 않는다. 게시·커밋·푸시는 해당 요청의 권한 범위에 따른다.

## 검토와 전달

1. 기술 설명이 맞고 근거와 실행 여부를 정확하게 표현했는가?
2. 저자가 말하지 않은 생각·감정·성공·원인 이해를 1인칭으로 추가하지 않았는가?
3. 기술 설명을 정돈하면서 혼잣말·삽질·감정과 판단이 바뀐 이유를 지우지 않았는가?
4. 느낌표·말줄임·농담이 내용에서 나왔는가, 저자답게 보이려는 흉내인가? 내용에서 나온 것은 새 표현이어도 남긴다.
5. 정보가 없는 부분을 형식·비유·이미지로 부풀리지 않았는가?
6. 사실을 지키는 선에서 이 글이 읽을 만한가? 도입이 독자를 붙잡는가, 설명 순서가 가장 이해가 빠른 순서인가? 이 항목을 이유로 1~5번을 완화하지 않는다.
7. 삭제 테스트: 한 문장씩 지워봤을 때 정보가 줄지 않는 문장을 지운다.
8. 대체 가능성 테스트: 다른 주제 글에 그대로 옮겨 붙일 수 있는 문단은 이 글만의 내용이 없다. 소제목 형태·목록 항목 수·문단 길이가 전부 같은 모양인지도 본다.

기계 검사는 문체의 진위를 판정하지 않는다. 변경 파일, 핵심 보완, 사용자 답변이 필요한 부분, 실제 수행한 검증을 짧게 보고한다. 수정 제안과 실제 반영을 구분한다.
