# 블로그 포스팅

이 레포는 Jekyll(`kramdown` + GFM) + yat 테마 블로그다. 글은 `_posts/YYYY-MM-DD-slug.md`.
**문체는 `voice.md`가 기준이다. 초안을 쓰기 전에 반드시 읽는다.** 2026-07 이전 161편을 실측해 만든 프로파일이다.

경로는 전부 레포 루트(`bbie-6772.github.io/`) 기준.

## 절대 규칙

1. **한 번에 완성본을 뱉지 않는다.** 아래 5단계를 순서대로 밟고, 각 단계 끝에서 사용자에게 확인받고 넘어간다.
2. **결정이 필요하면 묻는다.** 시리즈 번호, 분량, 어디까지 다룰지, 어떤 경험과 엮을지 — 추측하지 말고 `AskUserQuestion`으로 선택지를 준다.
3. **글은 한국어.** 코드·용어·고유명사만 영어.
4. **12세 비전공자가 읽어도 이해되게.** 전문 용어는 쓰기 전에 한 문장으로 풀어준다.
5. **사용자가 실제로 겪지 않은 경험을 지어내지 않는다.** 경험을 엮으려면 2단계에서 물어본다.

## 0단계 — 무엇을 쓰는 글인지 확정

먼저 두 축을 정한다. 사용자가 안 밝혔으면 묻는다.

**[분류]**
1. 기존 시리즈에 추가 → 이전 편들과 이어지는 도입부·번호가 필요하다
2. 새 시리즈 시작 → 시리즈 전체 로드맵을 개요에 깔아야 한다

**[초점]**
1. 학습 내용 정리 → 섹션이 개념 단위 (개념 → 비유 → 수식/표 → 정리)
2. 프로젝트 진행·트러블슈팅 회고 → 섹션이 사건 단위 (증상 → 가설 → 코드 → 원인 → 수정 → 전후 비교)

주제만 보고 판단이 서면 판단하고 한 줄로 알리되, 갈리면 묻는다.
**둘 다 아래 「글의 뼈대」를 그대로 쓴다.** 초점은 섹션을 무엇으로 채우느냐만 바꾼다.

### 기존 시리즈면 맥락부터 읽는다

```bash
grep -h "^categories:" _posts/*.md | sort | uniq -c | sort -rn | head -10
```

```bash
grep -l "^categories: ssafy" _posts/*.md | sort | tail -3 | xargs grep -h "^title:\|^subtitle:"
```

→ 다음 편 번호와 subtitle 작명 패턴이 나온다. (`SSAFY - < 25 >` / `딥러닝과 영상 모델 - 좋은 구조만으로는 부족하다, 학습 전략`)
직전 편 본문도 최소 1편은 읽는다. 도입부에서 "22~24편은 ~의 이야기였다" 식으로 이어붙여야 한다.

## 1단계 — 리서치

- 주제의 사실관계를 조사한다. 최신 수치·버전·논문 연도가 걸리면 `WebSearch`로 확인한다.
- **출처가 갈리는 항목은 갈린 채로 기록**해뒀다가 2단계에서 사용자에게 확인받는다.
- 레포 안에 이미 다룬 적 있는 주제인지 본다. 있으면 그 글을 인용·연결한다.

```bash
grep -rl "키워드" _posts/ | tail -5
```

**단계 끝**: 조사한 내용을 개조식 5~10줄로 요약해 보여주고 "이 범위 맞나?" 확인받는다.

## 2단계 — 교차검증 Q&A

여기가 이 스킬의 핵심이다. **묻지 않고 쓴 글은 사용자의 글이 아니다.**

한 번에 3~4개씩, `AskUserQuestion`으로 묻는다. 물을 것:

- **이해도 확인** — 조사한 개념 중 헷갈리거나 이미 아는 부분이 어디인가. (아는 건 짧게, 헷갈린 건 길게 쓴다)
- **생각·의견** — 이 기술/상황에 대해 어떻게 느꼈나. 한줄 평에 그대로 들어간다.
- **경험 연결** — 이전 프로젝트(Ducktopia, TCP 멀티플레이, 타워디펜스, 스위프 SpringBoot, SSAFY 등) 중 무엇과 비교할까.
- **사실 확인** — 1단계에서 갈렸던 항목, 그리고 실제 코드·에러 로그·수치가 있으면 원문을 달라고 한다.
- **범위** — 이번 글에서 자를 지점. (다음 편으로 미룰 것)

트러블슈팅 글이면 추가로: 처음 세운 가설이 무엇이었고 왜 틀렸는지. **실패한 가설이 이 블로그 글의 알맹이다.**

**그리고 반드시 이미지를 요청한다.** 목차를 잡으면서 "여기엔 실제 화면이 있어야 한다" 싶은 자리를 골라
무엇이 찍혀 있어야 하는지까지 적어 목록으로 부탁한다. 자세한 판단 기준은 아래 「시각자료」 절.

**단계 끝**: 답변을 정리해 목차(소제목 목록)를 제안하고, **각 섹션에 들어갈 그림이 요청분인지 생성분인지 표시해서** 승인받는다.

### 글의 뼈대

2026-07 이후 55편(13,910줄)에서 뽑은 구조다. **문체는 `voice.md`(7월 이전), 구조는 이것(7월 이후).** 섞어 쓰는 게 맞다.

```
## 개요                     ← 45/55편. 지난 편과의 연결 + 이번 글의 질문 한 줄
> **이번 글이 답할 질문**    ← 개요 안에 인용으로 못을 박는다
---
## 1. 첫 번째 덩어리 — 짧은 부제
### 세부 항목
### 더 쉬운 비유로           ← 어려운 개념 뒤에 붙인다 (14회 등장)
---
## 2. 두 번째 덩어리 — 짧은 부제
   ... (편당 4~5개)
---
## 정리                     ← 30편. 글 전체를 개조식으로 압축. 볼드로 키워드
## 참고 자료                ← 외부 출처가 있을 때만. 링크 목록
## 한줄 평                  ← 54/55편. 진짜 한 줄
---
```

**편당 실측 목표치** (7월 이후 55편 평균 / 괄호는 7월 이전)

| 요소 | 편당 | 쓰는 법 |
|---|---|---|
| 본문 길이 | **253줄** (180) | 학습정리는 250~400, 회고는 100~200 |
| `## N.` 번호 섹션 | **4.5개** (0.04) | 섹션에 번호를 붙이고 ` — ` 뒤에 짧은 부제를 단다 |
| `---` 구분선 | **6.2개** (1.1) | 번호 섹션 사이마다. 이게 가독성의 절반이다 |
| `>` 인용 | **9.8개** (0.4) | 섹션의 결론 한 줄을 뽑아 인용으로 세운다 |
| 표 | **24줄** (2.6) | 비교·분류·용어 대응은 문장 대신 표로 |
| 이미지 | **2.8장** (1.5) | 「시각자료」 절 참고. 최소 2장, 없으면 글이 벽이 된다 |
| `$$` 수식 | **2.9개** (0) | 수식은 코드블록이 아니라 `$$`로 (db0a49a) |

지킬 것:

- **`>` 인용은 요약 도구다.** 섹션 하나를 다 읽고 하나만 기억한다면 무엇인가 — 그걸 인용으로 뽑는다. 남의 말 인용이 아니다.
- **번호 섹션의 부제는 결론을 미리 말한다.** `## 2. 활성화 함수` (X) → `## 2. 활성화 함수 — 일단 ReLU부터` (O)
- **어려운 개념 뒤엔 `### 더 쉬운 비유로`.** 12세 눈높이 요구를 이 섹션이 담당한다. 인용 3줄로 대조를 만들고, 일상 장면(요리, 물건 찾기)으로 한 문단.
- **`## 정리`는 새 내용을 넣지 않는다.** 본문에 이미 나온 것만 개조식 + 볼드 키워드로 압축한다.
- **설명이 30줄 넘게 글로만 이어지면 그림 후보다.** 수치를 나열하고 있거나, 단계를 말로 풀고 있거나, 두 가지를 대조하고 있으면 그건 그려야 할 것을 쓰고 있는 것이다. 「시각자료」 절로 간다.
- 회고글도 똑같이 쓴다. `## 1. 증상 — 무엇이 터졌나` / `## 2. 가설 — 처음엔 이렇게 봤다` / `## 3. 원인` / `## 4. 수정` / `## 정리`.

## 4단계 — 비판적 검토

먼저 기계 검사. **이 레포엔 ruby/bundler가 없어서 `jekyll build`를 돌릴 수 없다.** 대신 실제로 깨졌던 사례를 규칙화한 린터를 쓴다.

```bash
python .claude/skills/blog-post/lint.py _posts/2026-08-18-ssafy.md
```

ERROR 0건이 될 때까지 고친다. WARN 중 **`## 개요` / `## 정리` / `>` 인용 개수 / 60줄 연속 / 이미지 장수 / SVG 경계 초과** 여섯 가지는 「글의 뼈대」와 「시각자료」 검사라 신규 초안에서는 이것도 0건을 목표로 한다. 나머지 WARN은 판단해서 처리.

린터가 보는 것: 이미지 장수, `TODO:이미지` 자리표시자(남아 있으면 ERROR), 참조한 SVG의 XML 파싱과 `viewBox` 경계 초과.

그다음 사람 눈으로 볼 것 — 발견한 문제는 **고치기 전에 목록으로 보고**한다.

- **사실오류**: 연도·수치·논문명·API 시그니처. 확신 없으면 다시 검색한다.
- **문법·맞춤법**: 띄어쓰기, 조사, 비문. 단, `voice.md`에 적힌 구어체 습관(`..`, `!`, 괄호 보충)은 오류가 아니다. 건드리지 마라.
- **경험 왜곡**: 2단계에서 듣지 않은 감정·경험이 들어갔는가. 들어갔으면 지운다.
- **문체 이탈**: `또한`, `뿐만 아니라`, `결론적으로`, `~할 수 있습니다`, `여러분` — 하나라도 있으면 AI 티가 난다.
- **눈높이**: 12세가 못 읽을 문단이 있는가. 용어를 풀지 않고 던진 곳이 있는가.
- **구조**: 「글의 뼈대」대로인가. `## 개요` → 번호 섹션 → `## 정리` → `## 한줄 평`. 번호 섹션 사이에 `---`가 있는가. 섹션마다 `>` 요약이 하나씩 있는가. 한줄 평이 진짜 한 줄인가.
- **덩어리 크기**: `---` 없이 60줄 넘게 이어지는 구간이 있으면 섹션을 쪼갠다. 이게 최근 글이 읽히는 이유다.
- **시각자료**: 이미지가 2장 이상인가. 실물이 있는 자리를 생성 그림으로 때우지 않았는가. `TODO:이미지` 자리표시자가 남아 있으면 **확정 전에 사용자에게 다시 요청**한다. 만든 SVG는 XML 파싱과 좌표 경계를 확인했는가.

## 5단계 — 확정

검토 결과를 반영해 파일을 수정하고, `lint.py`를 한 번 더 돌려 ERROR 0을 확인한다.
커밋은 사용자가 요청할 때만 한다. 요청하면 기존 메시지 형식을 따른다: `[posts] ...` / `[fix] ...`

## Jekyll 함정 (전부 이 레포에서 실제로 깨졌던 것)

| 함정 | 증상 | 대처 |
|---|---|---|
| `$$` 안의 `\{` `\}` | kramdown이 백슬래시를 먹어 `\left{` 이 되고 수식 전체가 LaTeX 원문으로 노출 (7f6360e) | `\lbrace` `\rbrace` |
| 수식 안 `\%` | 백슬래시가 먹히면 `%`가 LaTeX 주석이 되어 **뒷부분이 통째로 사라짐** | 퍼센트는 수식 밖으로 |
| 수식 안 `\\` 줄바꿈, `aligned` | 같은 이유로 깨짐 | `$$` 블록을 나누거나 표로 |
| 수식 안 `<` `>` | HTML로 이스케이프됨 | `\lt` `\gt` |
| `$$`가 문단에 붙어 있음 | 렌더 실패 | `$$`는 단독 줄 + 앞뒤 빈 줄 |
| 표 셀 안의 `|` (유니온 타입 `A \| B`) | 열 수가 어긋나 표가 통째로 문단이 됨 | `\|` 로 이스케이프 |
| 본문의 `{{` `{%` | Liquid가 해석해 빌드 실패/증발 | 코드블록 안에 넣거나 `{% raw %}` |
| 코드블록 안 박스문자 `─│┌┐└┘` | monospace 폴백에서 폭이 섞여 정렬 붕괴 (857b6ba) | 수식은 `$$`로, 다이어그램은 라벨 나열로 |
| `title:`에 `: ` 또는 ` #` | YAML 파싱 실패 | 따옴표로 감싼다 (`C#`처럼 앞에 공백 없는 `#`은 안전) |
| 파일명에 공백 (`2024-12-13-bootcamp .md`) | 퍼머링크가 깨짐 | `YYYY-MM-DD-slug.md` 엄수 |

**백슬래시 뒤에는 알파벳만 온다** — 이 한 줄만 지키면 수식 사고 대부분이 안 난다.

## 시각자료

**글보다 그림을 먼저 생각한다.** 최근 글이 읽히는 이유의 절반은 구조, 나머지 절반은 그림이다.
다만 **그림을 전부 만들어내면 안 된다.** 이 블로그의 원래 방식은 실제 화면 캡처였다.

| 시기 | 편당 이미지 | 직접 업로드 | 생성 자산 |
|---|---|---|---|
| 7월 이전 161편 | 1.5장 | **204장 (86%)** | 0장 |
| 7월 이후 55편 | 2.8장 | 27장 (18%) | **125장 (82%)** |

> **양은 최근 수준(편당 2~4장), 출처는 예전 방식(실물 우선).** 실물이 있는데 그림으로 대신하면 글의 신뢰가 깎인다.

### 요청할 것 vs 만들 것

**판단 기준은 하나다 — 이 세상에 실물이 존재하는가.**

| 존재한다 → **사용자에게 요청** | 존재하지 않는다 → **직접 생성** |
|---|---|
| 에러 메시지·터미널 출력·로그 화면 | 개념 설명 그림, 비유를 그린 것 |
| 실행 결과, 동작하는 화면, 전후 비교 | 수치 비교 그래프, 통계 시각화 |
| 관리 콘솔·대시보드·설정 화면 | 흐름도, 아키텍처 구성도, 순서도 |
| 팀에서 공유받은 자료, 회의 정리본 | 분류표를 그림으로 옮긴 것 |
| 강의·발표 자료 중 공개 가능한 것 | 대외비 자료를 대체할 재구성 그림 |

**실물이 있는데 "비슷하게 그려주기"는 하지 않는다.** 그건 없는 증거를 만드는 일이다.

### 언제 어떻게 요청하나

**2단계(질의응답)에서 목록으로 요청한다.** 초안을 다 쓰고 나서 "이미지 주세요"는 늦다 — 이미 글이 그림 없이 완성돼 버린다.

요청은 **구체적으로** 한다. "스크린샷 주세요"로는 원하는 게 안 온다.

> 나쁜 요청 — "에러 화면 있으면 주세요"
> 좋은 요청 — "헬스체크가 끊길 때 터미널에 찍힌 로그, 스택이 3까지 쌓인 순간이 보이는 걸로 한 장 부탁드립니다"

받은 이미지는 사용자가 GitHub에 올린 URL(`https://github.com/user-attachments/...`)을 그대로 본문에 넣는다.

**사용자가 "없다 / 못 준다"고 하면 억지로 만들지 않는다.** 순서대로 물러선다.

1. 그 자리를 개념 그림이나 표로 바꿀 수 있는가 → 바꾼다
2. 없어도 글이 서는가 → 뺀다
3. 없으면 글이 안 서는가 → 그 대목을 글에서 덜어낸다

### 생성할 때 (SVG)

- 위치: `assets/images/<시리즈-슬러그>/NN-이름.svg` → 본문에서 `/assets/images/blog-skill/01-style-metrics.svg`
- 기존 자산과 **같은 규격**으로 만든다 (`assets/images/ssafy-vision/` 참고)

| 항목 | 값 |
|---|---|
| 크기 | `viewBox="0 0 720 300~400"`, `width="100%"` |
| 폰트 | `Pretendard, -apple-system, Segoe UI, Roboto, sans-serif` |
| 배경 | `#f7f9fb` (모서리 `rx="12"`) |
| 카드 | 흰 바탕 + 테두리 `#d5dde6` |
| 글자 | 제목·본문 `#1d3a5c`, 보조 설명 `#6b7f95` |
| 강조 | 파랑 `#3d6fa8` / 연파랑 `#8fb0d4` / 경고·대비 `#a04040` |

- 그림 하나에 **한 가지만** 말한다. 표를 그대로 옮긴 그림은 표보다 못하다.
- 만든 뒤 **XML 파싱과 좌표 경계를 확인한다.** 텍스트가 `viewBox` 밖으로 나가면 잘린다.
- 다크 모드 대응은 하지 않는다 (기존 자산 전부 고정 밝은 배경, 통일이 우선)

### 대외비

**교육 자료·강의 슬라이드 원본은 싣지 않는다.** 개념만 재구성해 직접 그리고, 개요에 그 사실을 한 줄 밝힌다. (SSAFY 시리즈 관례)
