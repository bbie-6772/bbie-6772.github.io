## Node.js 게임서버개발 강의

### 게임 개발의 흐름

#### 기획 단계

1. PD(Project Director)가 게임 프로젝트의 기획안을 문서화하여 AD(Art Director) / TD(Technical Director) 에게 전달한다.

2. 기획안을 보고 AD는 컨셉아트를, TD는 프로토타입 게임을 여러 시안으로 제안한다.

3. 기획안과 프로토타입의 가능성을 보고 폐기 또는 새로운 프로젝트로 승격시킨다.

#### 개발 단계

백엔드(서버) 개발 입장에선 인프라 구성, 팀원 모집, 서버 로직 개발 등을
진행하지만 전체적으로 업무강도가 강하지 않다.

1. 인프라 구성

    - 대규모 트래픽처리를 위한 분산 서버 구성

    - 업데이트 방식 설계

    - 서버관리, 모니터링 툴 적용

    - NAS(네트워크 결합 스토리지), 내부망, 클라우드 세팅

2. 팀원 모집

    - 인프라, 클라우드, DBA, 웹, 게임서버 관련 인력 모집

3. 서버 로직 개발

    - 오픈 컨텐츠 개발 대응

    - 더미테스트, 부하테스트

    - 내/외부 QA 대응

#### 라이브 단계(서버 오픈)

오픈 초기에만 여러 이슈대응 및 서버 관리를 위한 로그 모니터링의 업무강도가 좀 되나, 이후에는 점점 줄어들게 된다.

- 초반 이슈 대응

- 게임 컨텐츠 개발

- 각종 이벤트 대응

### 게임 서버의 역할

개발자의 입장에서 검증(Verification)하는 역할을 한다.

- 예시

> LOG : 플레이어1 이 포션을 사용하여 HP을 100 회복 하였다.

1. 포션이 실제하는 아이템인가?
2. 플레이어의 HP가 100 증가 되었는가?

=> 이러한 검증을 하여 실패할 경우 버그, 이슈로 간주함

### HTTP와 TCP, WebSocket

#### HTTP (1.1 기준)

1. HTTP 형식은 Request가 발생할 때만 Response가 반환되기에,
비연결성이라는 특징을 가지고 있다.

    => 이러한 특징으로 연결 유지에 필요한 리소스가 적으며 처리가 빠르다.

2. stateless(무상태)란 이전의 사용자가 무슨행동을 하였는지와 상관없이 동일한 행동을 하는 것을 의미한다.

    => 기존의 사이트들은 유저 경험을 위해 세션,쿠키,DB를 이용하여 state(상태)를 저장한다.

3. HTTP 메세지 구조

    ![구조](https://blog.kakaocdn.net/dn/bfQp8o/btqCSgZUZsI/LQ6Uqsv6WKKQkAkNAjs711/img.png)

    - 위의 구조에 따르면 Header에 General Header 와 Req/Res에 따라 헤더를 추가로 더하고 바디까지 합쳐 주고 받는데..

    ![req](https://res.cloudinary.com/thewebmaster/image/upload/c_scale,f_auto,q_auto:best,w_1600/img/hosting/hosting-articles/http-request.jpg)

    ![res](https://res.cloudinary.com/thewebmaster/image/upload/c_scale,f_auto,q_auto:best,w_1600/img/hosting/hosting-articles/http-response.jpg)

    => 구조상 데이터가 많다..

4. 통신 방식

    위의 데이터를 OSI 7계층을 거쳐 주고 받기에 느려 연결성이 좋지 못하다.

    ![OSI7계층](https://oopy.lazyrockets.com/api/v2/notion/image?src=https%3A%2F%2Fs3-us-west-2.amazonaws.com%2Fsecure.notion-static.com%2Fbcca0270-dce1-425e-9fe7-6a8b5d7b17f9%2FUntitled.png&blockId=d009b6c2-a12b-45fe-997f-4594e88c12f9)

    => 이러한 계층을 줄여서 연결지향성 특징을 가진 프토로콜이 TCP!

    => 또한 TCP의 연결지향성 특징을 구현해 HTTP와 호환가능하게 만든 프로토콜이 WebSocket!  
    (하지만 대부분은 성능최적화로 인해 TCP가 더 빠르다네요)

#### TCP

HTTP의 비연결성과 다르게 TCP는 연결지향성을 갖는 프로토콜이다

1. 3-way-handshake*

2. 4-way-handshake*

3. 양방향 통신(Full-Duplex)*

#### WebSocket

HTTP나 TCP보다 Header에서 주고받는 데이터가 더욱 적어 오버헤드가 낮다.

1. 실시간 통신

2. 양방향 통신(Full-Duplex)

3. 지속적 연결*

4. 낮은 오버헤드*

5. HTTP와의 호환성

### 서버로직 이론

Data table을 서버와 클라이언트가 각각 소유하여,

클라이언트가 서버에게 요청을 할 때 클라이언트가 소유한 Data가 서버의 Data와 똑같은지 검증을 하게된다.

CDN(콘텐츠 전송 네트워크)을 이용하여 클라이언트와 서버에게 동일한 Data를 제공하도록 설계할 수 있다.
(클라이언트/서버 역할에 따라 주어지는 정보의 종류/정보량은 다를 수 있다.)
