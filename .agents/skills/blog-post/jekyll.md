# Jekyll 파일 작성과 검증

대상 블로그는 bbie-6772.github.io이며 kramdown/GFM과 yat 계열 구성을 사용한다. 실제 작업에서는 `_config.yml`, 인접 포스트, 설치 도구를 확인한다. 아래 예시는 저장소 관례이며 다른 환경의 절대 규칙이 아니다.

## 파일과 메타데이터

- `_posts/YYYY-MM-DD-slug.md`를 사용한다. 시리즈 번호·카테고리·태그는 인접 글과 맞추고 추측으로 번호를 만들지 않는다.
- 기존 글 수정 시 게시일·URL을 유지한다. 새 글 날짜는 사용자의 요청 또는 현지 날짜를 기준으로 한다.
- front matter의 `layout`, `title`, `subtitle`, `author`, `categories`, `banner`, `tags`를 인접 글에서 확인한다. 통상 author는 `bbie`다.
- `: `, ` #` 등이 들어간 YAML 값은 적절하게 따옴표로 감싼다. 긴 본문·코드에는 언어 태그가 있는 코드블록을 쓴다.
- 배너는 시리즈에서 실제 사용 중인 것을 재사용한다. 공통 배너 교체 요청이면 기존 자산을 보존하고 버전을 추가하며 요청 범위의 참조를 함께 갱신한다.
- 실물 이미지는 제공된 자산 또는 URL을 사용한다. 로컬 자산은 프로젝트의 `assets/images/<series>/` 아래에 두며 임시 경로를 참조하지 않는다.

## Liquid·수식

Jekyll은 코드블록 안에서도 Liquid를 처리한다. 코드 예제에서 `{{ ... }}`나 `{% ... %}` 자체를 보여주려면 그 예제를 `{% raw %}`와 `{% endraw %}`로 감싼다. 코드블록만 추가해 해결됐다고 보고하지 않는다.

`{% post_url ... %}`, `{% link ... %}`처럼 의도한 태그는 그대로 유지하고 대상 파일을 확인한다. 문법에 중괄호가 있다는 이유만으로 삭제하지 않는다. 실제 Liquid 설정도 확인한다.

수식은 현재 Markdown/MathJax 설정에 따라 렌더링을 확인한다. 이 블로그에서는 별도 줄의 `$$` 블록과 앞뒤 빈 줄이 유용하다. 과거 `\{`, `\}`, `\%`, `\\` 관련 문제가 있었지만 모든 백슬래시를 무조건 바꾸지 않는다. 렌더링이 깨진 경우 `\lbrace`, `\rbrace`, 수식 블록 분리 등을 검토한다.

표 안의 파이프·백슬래시·인라인 코드는 간이 검사가 오탐할 수 있다. 원문과 렌더링으로 확인한다.

참고: [Jekyll 공식 Liquid 태그 문서](https://jekyllrb.com/docs/liquid/tags/).

## 필요한 경우의 개념도

그림 수를 채우기 위해 생성하지 않는다. 실제 화면·로그와 개념 그림을 구분한다. 기존 시리즈 디자인이 있으면 따른다. 기존 밝은 SVG 스타일을 재사용할 경우:

- `viewBox="0 0 720 360"` 등 내용에 맞는 높이, `width="100%"`.
- `Pretendard, -apple-system, Segoe UI, Roboto, sans-serif`.
- 배경 `#f7f9fb`, 흰 카드, 테두리 `#d5dde6`, 글자 `#1d3a5c`와 `#6b7f95`.
- 강조 `#3d6fa8`, `#8fb0d4`, 대비 `#a04040`.

한 그림에 한 가지 관계를 설명한다. XML 파싱과 실제 화면에서 글자 잘림·가독성을 확인한다. 좌표 검사만으로 시각 검증을 완료했다고 쓰지 않는다. SSAFY 교육 자료는 원본을 그대로 게시하지 않는 기존 관례를 지키고 개념을 재구성한 경우 밝힌다.

## 간이 검사 실행

Python 3 표준 라이브러리만 사용하는 `lint.py`가 스킬 폴더에 있다. 저장소 루트에서 실행한다. `SKILL_DIR`는 예시 자리이므로 실제 설치 위치로 바꾼다.

```text
python "SKILL_DIR/lint.py" "_posts/YYYY-MM-DD-slug.md"
```

Codex에서는 `.agents/skills/blog-post/lint.py`, Claude Code에서는 `.claude/skills/blog-post/lint.py`일 수 있다. 설치 위치를 실제로 확인하며 절대 Windows 경로를 가정하지 않는다. 여러 파일 또는 `_posts` 디렉터리도 받을 수 있다.

ERROR는 수정하거나 오탐인지 확인한다. WARN은 문맥에 따라 판단한다. 줄 수·이미지 장수·요약 개수·고정 소제목을 만족시키기 위한 편집은 하지 않는다. 이 검사는 얕은 YAML/Markdown 검사로 완전한 파서나 Jekyll 빌드를 대체하지 않는다.

Ruby/Bundler가 사용 가능한지 확인하고 프로젝트의 빌드 절차를 따른다. 실행 환경이 없으면 간이 검사 범위와 빌드 미실행을 보고한다. 관련 없는 과거 글 오류를 요청 없이 모두 수정하지 않는다.

Claude에서 저장소나 실행 도구가 없는 경우에는 제공된 Markdown과 자료로 글을 작성·검토하고 검사 미실행 사실을 알린다. 존재하지 않는 파일 접근이나 실행 결과를 주장하지 않는다.
